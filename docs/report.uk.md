# RotorLoop — Лаб 01: Event loop — це і є ігровий цикл

**Ідея:** аркадна FPV-арена, у якій видно різницю між кроком симуляції та кадром зображення. Квадрокоптер — візуальна тема для передбаченої курсом фізики корабля; це не симулятор аеродинаміки.

## Як запустити й керувати

Потрібен Node 24; перевірено на 24.20.0. У корені проєкту: `npm ci`, потім `npm run dev`. Якщо використовується nvm: спочатку `nvm install` і `nvm use`. W/↑ — тяга вперед, A/D або ←/→ — yaw, R — одноразове скидання. На вузькому екрані інтерфейс адаптується, але touch-керування не реалізоване.

## Основні інженерні рішення

1. **Один власник часу.** Тільки `createLoop` планує production rAF. Перший callback задає часову базу; наступні додають до акумулятора не більше 0,25 с. Фізика отримує лише `1/60` с. Рендер може мати нуль або кілька кроків перед собою.
2. **Стани відокремлені від пікселів.** `integrate` повертає новий plain object. Renderer змішує previous/current за alpha. Для кута береться найкоротша дуга; після wrap синхронізується тільки відповідна попередня координата. Ціна простого wrap-рішення — один крок без інтерполяції по цій осі.
3. **Одиниці вимірювання явні.** Позиція — CSS px, швидкість — CSS px/с, кут — радіани, dt — секунди. DPR змінює backing resolution, а не фізику. FRAME у HUD — інтервал між callback, а не час виконання draw.
4. **Замикання має життєвий цикл.** Sets приховані всередині input; повторний keydown не створює нового edge. Blur/hidden очищає введення, destroy прибирає слухачів. HMR прибирає старий цикл та підписки.
5. **Метрики не прикрашають інтерфейс.** SIM/DISPLAY рахують фактичні події. Смужка alpha показує реальний залишок акумулятора. Вигаданих батареї, RSSI або «стабільних 120 FPS» немає.

Константи залишені після реальної перевірки клавіатурою: поворот 3 рад/с (повне коло приблизно 2,09 с), прискорення 480 px/с², drag 1,2 с⁻¹ (півперіод швидкості приблизно 0,58 с), максимум 340 px/с (не більше 5,67 px за звичайний крок). Масштабного ручного playtest не заявляємо.

## Експеримент 1: блокування потоку

Chrome 152, реальний rAF, приблизно 10 с на прогін:

| Режим | Callback/с | Середній інтервал | p95 | p99 | Максимум |
| --- | ---: | ---: | ---: | ---: | ---: |
| Базовий | 120,01 | 8,333 мс | 9,10 мс | 9,30 мс | 10,30 мс |
| 100 мс busy-wait кожного 60-го рендера | 101,79 | 9,825 мс | 9,30 мс | 100,30 мс | 100,50 мс |

Зависання є рідшим за 5% кадрів, тому p95 майже не змінюється. Його добре видно в p99 та максимумі. Поки синхронний код утримує головний потік, інший callback введення чи малювання не може його перервати. Promise не переносить роботу в інший потік. Окреме числове вимірювання затримки клавіатури під busy-wait не проводилося.

Останнє вікно HUD: baseline — SIM **59,506**, DISPLAY **120,004**, FRAME **8,3 мс**; із блокуванням — SIM **60**, DISPLAY **98**, FRAME **99,9 мс**. Це короткі вікна вимірювання, тому вони відрізняються від середніх за весь прогін. Акумулятор наздоганяв фізику після кожного зависання.

## Експеримент 2: таймер проти rAF

`setInterval(..., 16)` дав **62,50 callback/с**, середній інтервал **16,000 мс**, SD **0,664 мс**. rAF дав **120,01 callback/с**, SD **0,355 мс**. Таймер отримує час через `performance.now()`, бо rAF timestamp він не передає.

Вкладки справді приховувалися приблизно на 5 с, і зміни visibility збережені. Найбільший інтервал rAF — **5032,9 мс**, таймера — **1000,3 мс**. Цей Chrome призупинив rAF і обмежив таймер приблизно секундною частотою. Не можна стверджувати, що таймери завжди працюють у фоні без обмежень. Clamp свідомо відкинув більшість пропущеного часу.

## Експеримент 3: змінний крок

Ті самі початкові x=100, y=300, нульова швидкість, напрям +x і постійна тяга. Застосовано справжній Chrome DevTools Protocol `Emulation.setCPUThrottlingRate`, значення 1 та 6. Накопичення координат не загортається, щоб краї арени не приховали похибку; загортається лише малювання експерименту.

| П'ять секунд wall time | x | y | Кроків |
| --- | ---: | ---: | ---: |
| Variable, 1× | 1614,301372 | 300 | 601 |
| Variable, 6× | 1613,789824 | 300 | 597 |
| Fixed, 1× | 1610,784130 | 300 | 300 |
| Fixed, 6× | 1610,784130 | 300 | 300 |

Variable-розбіжність — **0,511548 px**, fixed — **0 px**. Проте variable-прогони також завершилися при дещо різному фізичному часі. Тому додано контроль із рівно п'ятьма секундами симуляції: fixed — 300 кроків; variable — останній dt обрізається до залишку.

За однакового simulated time variable дав x=**1611,173389** та **1611,217935**: розбіжність **0,044546 px**. Fixed — **1610,784130** в обох випадках. CPU 6× залишив легку сцену близькою до 120 callback/с; великий ефект не вигадувався.

Окремий додатковий дослід додає **35 мс роботи в кожен render**: приблизно 28,45 callback/с; variable x=**1609,748862**, тобто відмінність **1,424528 px** від нормального exact-time прогону. Fixed знову x=**1610,784130**. Це штучно введена робота, а не підміна результату DevTools 6×.

## Чого ці результати не доводять

- Fixed dt сам по собі не гарантує ідентичного lockstep на всіх платформах: потрібні однакові стани, входи по кроках, порядок і математика.
- 60 steps/s — нормальний режим, не гарантія після довгої паузи чи перевантаження.
- Callback FPS не дорівнює незалежно виміряній кількості фізичних показів монітора.
- Один прогін описує цю сесію. Сирі дані й точний спосіб обчислення перцентилів доступні для повторення.

## Перевірки та захист

Пройдено 16 тестів, Biome і production build на Node 24.20.0. Браузер перевірив політ, поворот, одноразовий reset, загортання, очищення клавіш після приховування, повторні resize, DPR 1/2 і відсутність uncaught JS exceptions. Інженерний review знайшов перезапуск із callback, який створював дубль rAF; додано generation token і регресійні тести. Окремо виправлено DPR-only зміну, яка спочатку не проходила браузерний тест.

Повні [вимірювання та методика](evidence/RESULTS.md), [дослідження](research.md), [незалежний аудит](review.md) та [відповіді на всі Reflection](defense.md).

## Доповнення: телеметрія після початкової здачі

На `main` додано optional stretch з умови: Canvas-стрічка останніх 120 інтервалів, червона понад 16,7 мс. Клавіша H перемикає панель із mean/p95/max, кроками на callback, часом симуляції, загальними ticks, alpha та відкинутим clamp часом. На вузькому екрані панель спочатку прихована; на надто низькому не розгортається. R скидає дрон, але не статистику запуску.

Історія має 120 вибірок, а не сталу тривалість. Перший rAF не додає штучний нуль. Числові підсумки оновлюються приблизно кожні 250 мс, тому трохи відстають від графіка; стовпчики обрізані на 50 мс, числові значення зберігають необмежений інтервал. Червоний колір не доводить втрату фізичного кадру. Додано тести: тепер їх 19. Окрема [браузерна перевірка](evidence/telemetry-smoke.json) є функціональною, а не новим бенчмарком.

Сирі результати трьох експериментів вище належать початковим зафіксованим версіям; розширений HUD не вимірювався повторно в цих експериментах. Опублікований тег `lab-01` збережено на `0f134a2`.

Мультиплеєр починається у Лаб 04 (Node.js, WebSocket, кімнати), продовжується у Лаб 05 (серверний стан, prediction/reconciliation, бінарні snapshots) і публікується у Лаб 08. Чиста симуляція готова до повторного використання; спільні межі світу, серверний годинник і протокол введення ще потрібно реалізувати у відповідних лабораторних.
